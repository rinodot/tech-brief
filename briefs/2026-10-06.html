それでも抜けたのが 1 件。ドメイン名 fu-koro は運営者名なのに、AI は「符から取った」という由来をトップページに書き、テストは全部通っていた。対処は CLAUDE.md に 1 行、ADR に 1 枚、全ページを確かめるテスト 1 本。含意: テストは「決めた正しさ」しか守らない。人間に残るのは、何を作るか言葉にし、正しさの基準を決め、使う人の目で見ること。n=1、自作アプリへのリンクあり。

— 9/17 既報の /goal を「何を渡すか」まで具体化した運用の型。公式 docs の条件の書き方（測れる終端＋確かめ方＋制約）と噛み合う。

mizchi 氏（10/5）。人間の役割はループの構築・評価指標の作成・テストと CI の調整で、「数値化できるものなら AI で自動化できる」。問題を洗い出す→Umbrella Issue にまとめる→/goal Issues を全部潰して で順に処理。指標は RSS・hyperfine、Lint 警告数・循環複雑度、Mutation Test の Kill 率、VRT の一致率。含意: 自分の仕事を「基準を数値にする」側へ寄せるほど、Claude Code に渡せる範囲が広がる。実測値はなく、著者も「またすぐ変わる」と留保。

試すなら: 直したい点を Issue に分けて 1 本の Umbrella Issue にぶら下げ、各 Issue に「flutter test が exit 0」「dart analyze の warning 0」「hyperfine で起動 N ms 以下」のように測れる終端を書く → auto mode で /goal Umbrella Issue #N の子 Issue を全部閉じる。or stop after 20 turns → 途中経過は /goal（引数なし）、止めるなら /goal clear。無人なら claude -p "/goal …" --output-format stream-json --verbose（/goal はターン終了ごとに小型モデルが条件を判定する Stop フックの包み紙。条件は「測れる終端・確かめ方・制約」で最大 4,000 字、ターン上限の句も書ける — docs/en/goal で確認。指標の選び方は記事本文）。

sqflite のマイグレーションは「古いスキーマの DB を実際に作り、新コードで開く」テストで守る — sqflite_common_ffi でテストから本物の SQLite を開き、PRAGMA table_info で新規作成と移行後の列定義を比べたら NOT NULL と DEFAULT が食い違っていた

— 公開済み Flutter アプリの DB 変更で一番怖い「既存ユーザーの端末でだけ壊れる」を、実機なしのテスト 2 本で公開前に捕まえる型。

hk_work 氏（10/4）。shelf_id 列を足す移行を、databaseFactoryFfi のテストで実機なしに検証。v1 の CREATE TABLE で古い DB を作り 1 件 insert→本番の DB クラスで開き直し、onUpgrade 後に行と新列を expect。PRAGMA table_info では新規作成が notnull 1・default 1、移行後は notnull 0・default null（NOT NULL 列には DEFAULT が必須）。含意: 公開後なら移行がもう 1 段要る差を、公開前に止めた。

試すなら: dev_dependencies に sqflite_common_ffi: ^2.4.3（pub.dev 最新、9/10）を足す → test/ に「v1 の CREATE TABLE で作って 1 行入れる→自分の DB クラスで開く→行と新列を expect」と「新規作成と移行後の PRAGMA table_info を比べる」の 2 本を書き、flutter test で回す → 新列は NOT NULL なら必ず DEFAULT を付ける（sqfliteFfiInit() と databaseFactoryFfi は pub.dev の README、コードと列定義の差は記事本文）。
