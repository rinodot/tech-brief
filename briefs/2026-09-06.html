Flutterアプリの公開作業をClaude Codeに任せた実例 — 114項目のQAは「Markdownに○×と日付を書かせる」で回した

— 自分のアプリの次のリリースに、そのまま持ち込める分担と手順が書いてある。

きしまる（LEATEQ）氏が8/31にZennで公開した実例。Subrep（サブスク管理、Android）をFlutter＋drift＋RevenueCatで作り、実装は2日ほど、自動テストは160件。QAはリポジトリに置いた114項目のMarkdownをClaude Codeが1項目ずつ検証し、○×と日付を書き込んでコミットで証跡を残す方式で、セッションが切れてもファイルから再開できる。

通知はエミュレータの時刻をadb shell "date 0901090026 && am broadcast -a android.intent.action.TIME_SET"で進め、実時間を待たずに発火条件を踏ませた。ストア素材はPNGのIHDRチャンクを読む自作パーサで、9:16のスクリーンショットと1024×500のフィーチャーグラフィックを送信前に検査。Play Consoleの入力もブラウザ操作で代行。人が握ったのは支払い・審査送信のボタン、実機で触った「もっさり」の判断、審査中はコードを変えない決定。8/7内部テスト、8/13審査提出、8/21公開。含意: 任せる範囲を項目単位で明文化した点が型になる。

試すなら: リポジトリに qa/checklist.md を置き「1項目ずつ検証して、結果と日付を書き込んでコミットして」と頼む。通知は adb shell "date MMDDhhmmYY && am broadcast -a android.intent.action.TIME_SET" で時刻を進めて確認する。

OllamaがCPUへ逃がした8層をnum_gpuで戻すと3.7→30 tok/s — 16GBで116Kコンテキスト

— VRAMが余っているのに遅いとき、疑う場所が1つ増える。

Miyuki-Yumeno氏が9/4にZennで公開。RTX 5060 Ti 16GBで、Qwen3.8系の12GB量子化モデルをnum_ctx 118,784で動かすと3.71 tok/s。ログでは66層中58層しかGPUに載っていなかった。Ollamaの自動見積もりが保守的なためで、ModelfileにPARAMETER num_gpu 66を書いて全層をGPUへ載せると約30 tok/s、VRAM 15,779/16,311 MiB。含意: 見るべきはollama psのGPU%ではなくログの層数。

試すなら: Modelfileに FROM <model>:latest／PARAMETER num_ctx 118784／PARAMETER num_gpu 66 の3行を書いて ollama create <name> -f Modelfile。起動ログの offloaded N/M layers to GPU が N=M になっているか確認する。

特集: プロンプトキャッシュの原理 — 「先頭一致」がすべてで、$0.25の読みはそこからしか生まれない

Claude Codeは毎ターン、システムプロンプト・プロジェクト文脈（CLAUDE.mdなど）・会話履歴の全部をAPIへ送り直す。モデル側に記憶はない。速くて安いのは、APIがリクエスト先頭からの一致部分（prefix）を直近の処理済み内容と突き合わせ、一致分は再計算せずキャッシュ読みで課金するからだ。一致は完全一致で、途中が1文字変わればそこ以降はやり直し。部分キャッシュはない。

Fable 5.1は入力$10/MTokに対し、キャッシュ書きが$12.50（5分TTL）か$20（1時間TTL）、読みは$0.25。読みは基本の0.025倍で、他モデルの0.1倍より深い。書きは高いが、同じprefixを読むほど得になる。寿命は使うたびに延びる。

変わりにくい層を前に置く3層構成なので、会話が伸びるだけなら前の2層は当たり続ける。壊すのは前の層に触る操作: /modelと/effort（それぞれ別キャッシュ）、fast modeのON、prefixにツール定義が載るMCPサーバーの接続/切断、Bash丸ごとのdeny、/compact、Claude Codeの更新。壊さないもの: ファイル編集、CLAUDE.mdの編集（ただし次の/clearまで反映されない）、Skillsの呼び出し、/rewind、サブエージェント起動。

寿命はサブスク枠内の主会話が1時間、サブエージェントや/compactの要約、APIキー利用時は5分。キャッシュはマシン＋作業ディレクトリ単位で、worktreeを並べると別キャッシュになる。/usageのPrompt cache (main)行でキャッシュ比率・ミス回数・warm/coldと、v2.1.260からはミスの推定原因が見える。含意: 今週の「Fable 5.1は同じ枠でより多く回せる」はこの0.025倍が土台。モデルとeffortは冒頭で決め、切り替えは区切りで。

試すなら: /usage で Prompt cache (main) の比率とミス原因を見る（v2.1.251以降、原因表示は v2.1.260以降）。APIキー運用なら settings.json に "promptCacheTtl": "1h"（v2.1.242以降）。claude -p "hello" --output-format json の usage.cache_creation に ephemeral_1h_input_tokens が出れば1時間TTLが効いている。

出典: Claude Code docs — How Claude Code uses prompt caching
