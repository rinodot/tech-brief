Claude Code v2.1.287 で「Mods」が使えるようになった — プラグインに入れた JS の関数が Claude Code の中で動き、ツール呼び出しを止めたり書き換えたり、プロンプト上の帯やペインを描ける。作るのは「make a mod that …」と頼むだけで、ターン終了ごとに自動リロード

— 9/27 特集②「止めるのはフック」の次の段。設定フックは外のシェルで止める・記録するだけだったが、Mods は Claude Code の画面と挙動そのものを足せる。

公式 docs（10/1）。Mod はプラグインの一種で、hooks.json の modules が指す JS／TS が Claude Code のプロセス内で動く。hook は on('tool.call', ($, e, next) => …) の形で、イベントを観察・書き換え・肩代わり（next を呼ばない）の3通りで扱う。セッションで「make a mod that …」と頼むと組み込み skill plugin-authoring が ~/.claude/dev-mods/<session-id>/ に書き、「Enable for this session」でターン終了ごとにホットリロード。手書きなら claude --plugin-dir ./first-mod で読む。

注意は権限。Mod は自分の権限で動き、秘密を読め、ask ルールや PreToolUse フックが止めた呼び出しも承認できる。入れる前に claude plugin validate で握るイベントを一覧する。描画は CLI と Desktop の Code タブだけ（VS Code 拡張・claude -p では動くが描かれない）。含意: 「フックで止める」の次は、挙動そのものをコードで差し替える段階。

試すなら: claude --version が 2.1.287 以上なのを確認 → セッションで「make a mod that shows the current git branch above the prompt」と頼み「Enable for this session」→ 残したい mod は ~/.claude/dev-mods/<session-id>/<name>/ を ~/mods/ などへコピーして claude --plugin-dir ~/mods/<name> で読む → 同リリースの /plugin enable cc-plugin-you-should-know@builtin（見落としを横から指摘する組み込み mod）も1日試す（手順・コマンド・権限の注意は docs/en/plugins/mods/overview と /create、you-should-know は v2.1.287 のリリースノートで確認済み）。

Max 20x の使用枠は「出力トークンは入力の 5 倍、キャッシュ読みは 1/40」の重みで減っていた — プロキシで 220 リクエストを測った非公式の逆算。headless（claude -p）は 5 時間枠を対話の 2 倍、平日 21:00〜翌 3:00 は 2.86 倍の速さで消費

— 10/1 の「費用の 94% はキャッシュ読み」が、枠の消費でも効く理由。自動化ジョブを走らせる時刻とモデルを、この重みで決められる。

tksfjt1024氏（10/1）。プロキシで usage と使用率ヘッダを記録し、1% 進む量から逆算。重みは input 1・cache write 1.25・output 5・cache read 0.025。モデル係数は Haiku 4.5＝1 で Sonnet 5.5 が 1.5、Opus 5.5 が 2.2、Opus 5 が 2.75、Fable 5.1 が 10。headless は 5 時間枠を対話の 2 倍、平日 21〜翌 3 時は 2.86 倍で消費。含意: 枠はキャッシュを切らさない→自動化を深夜帯から外す→モデルを下げる、の順で守る。

試すなら: 定期実行の claude -p を平日 21:00〜翌 3:00 の外へ動かす → 同じ作業を Opus 5 と Opus 5.5 で回して /usage の進み方を比べる → 1 時間以上空く前に /compact（9/30 既報の TTL とこの重みの合わせ技。重みの表・測定法・9/18 の変更は記事本文。公式の係数ではないので自分の /usage で再確認）。

出典: Zenn — Claude Code の使用量はどう数えられているのか ── Max 20x で実測した重みは API 料金表と違った

ローカル RAG の埋め込みモデルを既定の nomic-embed-text から embeddinggemma に替えただけで、1 位正解率 25.9%→58.9%・MRR 0.336→0.676 — 521 チャンク・185 クエリの自前評価セットで 6 モデルを比べ、上位 4 つは統計的に差がないので「速さ」で選んだ

— 9/21 の「recall@5 90% でも正答 38%」、9/30 のリランキングに続く検索側の実測。再学習なし・GPU なしで、手元のコーパスで同じ比較ができる。

yuya_h氏（9/30）。個人ナレッジ検索 gbrain の日本語 521 チャンクに、手作り 35 問＋qwen3.5:4b 生成 150 問で Ollama の埋め込み 6 種を比較。最良は embeddinggemma（308M・768 次元）だが、上位 4 つ（qwen3-embedding・snowflake-arctic-embed2・bge-m3）は Cochran の Q 検定で p=0.449 と差がなく、決め手はバッチ速度（他の 2.4〜6.5 倍）。含意: 埋め込みは学習より選定、選定は自前の評価セットで。

試すなら: 自分のチャンクから qwen3.5:4b などに質問文を 100 本ほど生成させて評価セットにする → ollama pull embeddinggemma と nomic-embed-text の両方で埋め込み、hit@1／MRR を比べる → 同率なら速い方を採る（評価コードは github.com/yuya0408/gbrain-embedding-eval。数字と手順は記事本文、embeddinggemma のタグ名も記事の表記）。
