Claude Code チームのコードレビュー運用を公式が公開（10/15）: Claude が同リポジトリのコードの約 90% を書き、6〜9 月でマージ PR は 2 倍超・差し戻し率は 40% 超減。AI レビュアー導入で実質的なコメントが付く PR は 16%→54%、再レビューの平均は 2.08→1.32 回。鍵は REVIEW.md・3 ラウンド上限・差分だけ再レビュー・リスク別の承認（Low は人不要／High は 2 人）

— 10/11 特集④「別インスタンスでレビュー」「差し戻しは回数で止める」を、本家が数字つきで裏付けた。個人でも REVIEW.md と上限 3 回はそのまま使える。

Addy Osmani 氏ら（claude.dev、10/15）。Claude Code 自身のコードは約 90% を Claude が書き、6〜9 月でマージ PR は 2 倍超、差し戻し率は 40% 超減。AI レビュアー導入後、社内 PR で実質的なコメントが付く割合は 16%→54%。指摘され続けたものの約 59% は初回から残っていたコードで、対策は「3 ラウンドで止めて設計から考え直す」と「数回目以降は新しい差分だけ再レビュー」。これで 1 回で通る PR は 65%→78%、5 ラウンド以上は 8.9%→1.5%、平均 2.08→1.32 回。

承認はリスク別。Low（文書・フラグ裏の追加）は自動レビューと安全チェックが緑なら人は不要、Medium は 1 人、High（認証・課金・リリース）は 2 人。REVIEW.md はコードオーナーが書く短い文書で、「失敗はどう見えるか」（docs なら嘘、config なら誤経路）、細かい指摘の上限、飛ばすパス、根拠はファイルと行、件数から始まる要約を求める。含意: レビューの質は「何を見るか」の明文化と「いつ止めるか」の上限で決まる。注意: 社内モノレポの数字、個人規模の比較なし。

試すなら: リポジトリに REVIEW.md を置き「このコードで失敗はどう見えるか」「細かい指摘は N 件まで」「飛ばすパス」「根拠はファイルと行」の 4 点を書く → 作業の終わりに /code-review と /security-review（または文脈を持たない別セッションかサブエージェントのレビュー）→ PR テンプレートに「Testing」「Risk」「How to revert」を足す → 差し戻しは 3 回で止めて設計を見直し、4 回目以降は新しい差分だけ見せる → 事故と差し戻しを評価セットにし、レビュアーのプロンプトやモデルを変えたら採点し直す（公式の「How you can adopt this process」の順。Code Review 製品自体は Team／Enterprise の GA で Pro／Max は対象外）。

Claude Code の「直しました」を Stop フックで検査し、根拠のない完了報告を記録→次のターンで 1 回だけ注意を注入する仕組み。9/27〜10/16 の 4,331 返答で、証拠なしの完了は週ごとに 1.2%→8.3%→5.2%。言葉の見張りより効いたのは「作業の最後に AI 自身へ外から読み直させる手順」（キリヌキ自動化ラボ）

— 10/14 既報「出力側の門」の続き。禁止では消えない虚偽報告を「まず測る→次ターンで直させる」に変えた型。

キリヌキ自動化ラボ氏（10/16）。「直しました」が事実でない返答を検出する仕組み。Stop フックが最後の返答を読み、完了を示す語があるのに同じ段落に根拠がなければ記録。次の UserPromptSubmit で「直前の返答に根拠のない完了があった」と 1 回だけ文脈に足す。9/27 からの 4,331 返答で、証拠なしの完了は週ごとに 1.2%（2,430 中 30）→8.3%（818 中 68）→5.2%（889 中 46）。減らず、理由は未特定。含意: 門は「ゼロにする」より「見つけて次で直す」装置。n=1。

試すなら: .claude/settings.json に "Stop": [{"hooks": [{"type": "command", "command": "python reply_lint_min.py"}]}] と "UserPromptSubmit": [{"hooks": [{"type": "command", "command": "python reply_lint_inject.py"}]}] → スクリプトはフック入力の transcript_path から最後の返答を読み、完了語 (完了しました|できました|直りました|直しました|差し替えました|入れました|上がりました) と根拠 (開いて|測った|確かめました|照合|一致|\d+(?:\.\d+)?\s*(?:件|本|秒|%|枚|行|回)) を自分の語彙に置き換える → CLAUDE.md に「自己申告で『直った』と言わない。テストの終了コードと実物だけが根拠」「報告は開いた・測った物の数字を付ける」 → 1 週間ためて割合を見る（検出語を増やしたら週をまたいで比べない。フック仕様は docs/en/hooks、fail-closed は 10/13 既報）。

Riverpod 2.6.1→3.4.2 に上げたら「Cannot use the Ref of ＜provider＞ after it has been disposed.」で、ユーザーには「タップしても何も起きない」に見える不具合。原因は Provider より長生きした関数と、画面を閉じた後の state 代入。対処は用途別に ref.mounted・keepAlive・watch で寿命を揃える・サービスへ切り出し・ref.onDispose（日本トレカセンター 尾松氏）

— 自分のアプリも Riverpod 3 系。クラッシュとして記録されない沈黙の不具合なので、移行後は一覧→詳細の導線を手で踏む価値がある。

尾松氏（10/16）。flutter_riverpod 2.6.1→3.4.2 で、一覧をタップしても詳細が開かない。原因は①破棄済み Provider の関数を呼んだ ②画面を閉じた後に破棄済み Notifier へ state を代入。対処は用途別: 表示更新だけなら ref.mounted、必ず要る副作用は keepAlive か使う側の watch、保存はサービスへ、画面専用の通信は ref.onDispose。含意: Provider ごとに「誰が生かすか」を決める。ref.mounted は競合も取消も防がない。

試すなら: flutter pub deps | grep riverpod で 3 系か確認 → 一覧→詳細、保存→戻る、を実機で通し、ログで "after it has been disposed" を検索 → 出た箇所を「表示だけ／副作用／取り消したい通信」に分け、表示だけは await の直後に if (!ref.mounted) return;、副作用は @Riverpod(keepAlive: true) か呼び出し側の ref.watch、通信は ref.onDispose(cancelToken.cancel)（API docs の Ref.mounted は "Whether this Ref is still active"。可能なら onDispose を優先、と明記。記事の検証環境は Dart 3.13.1・riverpod 3.4.3）。
