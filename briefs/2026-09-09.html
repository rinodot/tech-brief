Claude Code は計画とレビューに残し、実装は安い側へ渡す — 63日・378回の委譲で完走85%、中央値683秒

— 週次上限が9/13で素に戻る前に、Claude Codeの「使いどころ」を絞る型として。

Sei氏が9/7にZennで公開。役割を4つに分け、Claude Codeは司令塔（仕様を書き、成果をレビュー）、実装はCursorをCLIから画面を開かず裏で走らせ、レビューと調査は別のClaudeセッションに持たせた。7/7〜9/7の63日で378回委譲し、85%が最後まで返ってきた。月別では7月73件（89%）、8月161件（81%）、9月は7日間で144件（86%）、1日あたり8→11→21件に増えた。成功した実行の中央値は683秒。

検証の型は3つ。実行前に基準値を取る（型エラー238件、通過テスト2,630件のように）、成果は自己申告でなく変更ファイルと指標の差分で受け取る、レビューは作業者と別のセッションに読ませる。Claude Code自身のトークンは減らず、1日の中央値は7月858Mから9月1,022Mへ約2割増え、空いた分が計画とレビューに回った。ただし9月分の95%はキャッシュの読み直しで、費用は2割増より小さい可能性がある。失敗58件の合計は26.9時間で全体の26%。含意: 分業で得るのは費用削減ではなく、Claude Codeの時間を考える仕事に寄せること。

試すなら: 委譲する前に flutter analyze と flutter test の件数を基準値として控え、実装役には「変更ファイル一覧と差分」を返させる。レビューは別セッションで claude -p "仕様と差分を照合して不足を列挙" に読ませる。

出典: Zenn — Claude Code は計画とレビューに残し、実装は安いモデルへ渡す

.claude の設定は「書けているのに黙って無視される」— matcher が効かないイベント10種と、プロジェクト設定では効かない71キー

— フックが「効いているつもり」問題の続き。今日は設定ファイルの側。

Quintet Kit氏が9/7にZennで公開、判定器 ccheck も公開。UserPromptSubmit・Stop など10のイベントは matcher を持たず、書いても無視され毎回発火する。if はツール系5イベント専用。プラグイン同梱のMCPツール名には plugin_<plugin>_ が挟まるので、サーバー名だけの matcher は当たらない。71の設定キーは user／managed 専用で、プロジェクトの settings.json では何も起きない。含意: 「読み込まれた」と「効いている」は別物。

試すなら: リポジトリのルートで npx @quintetkit/ccheck（Node 22.18以上）。指摘には根拠の公式ドキュメントURLが付くので、そのまま原典を確認する。

出典: Zenn — 設定は書けているのに、何も起きない

単発ベンチで3.6倍速いローカルLLMランタイムが、エージェントの実タスクでは遅かった — 犯人は1.5万トークンのツール定義のプリフィル

— ローカルLLMをエージェントに使うなら、tok/s より先に見る数字がある。

TK氏が9/7にZennで公開。単発ベンチは Rapid-MLX 66.7 tok/s、Ollama 18.6 tok/sなのに、Claude Agent SDKの実タスクでは Ollama 12〜15秒、Rapid-MLX 17〜18秒で逆転。毎回積む約19,000トークンの基礎コンテキスト（約15,000がツール定義）が原因で、Rapid-MLXのプリフィルが6.2秒→36.0秒に伸びた。ツール定義も圧縮する --pflash-include-tools で6.6秒に戻る。含意: 実プロンプト長でプリフィルを測る。

試すなら: ベンチのプロンプトに本番のツール定義（1万トークン超）を含め、Ollamaなら /api/generate 応答の prompt_eval_duration と eval_duration を分けて記録する。

出典: Zenn — ベンチで3.6倍速いランタイムが、実タスクでは遅い側だった話
