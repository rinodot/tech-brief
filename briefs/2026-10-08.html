Firestore の読み取り課金を 3 か月でおよそ半分にした手順 — Query Insights に出ないリアルタイムリスナー（onSnapshot）の読み取りを、データアクセス監査ログを BigQuery に流して「どのクエリが・どの端末から・何件返したか」で数え、最も重いクエリ 1 本（全体の約半分）から直した。監査ログは 1 日約 170GiB、既定のログバケットに溜めると月約 $2,500 になるので _Default シンクから除外する

— Flutter アプリの Firestore 読み取りは onSnapshot が主役。Query Insights で見えているつもりでも、公式ドキュメントどおり「リアルタイムリスナーは統計に含まれない」。課金の内訳を推測でなく数える道具の作り方として。

k_tkm 氏（10/7）。Query Insights は公式に「リアルタイムリスナーは含まれない」ので、onSnapshot 中心のアプリでは重いクエリが見えない。そこで監査ログの「データ読み取り」を BigQuery へ流し、methodName（Listen／RunQuery／BatchGet）・numResponseItems・callerSuppliedUserAgent（grpc-java＝Android）で「どのクエリが何件返したか」を集計。最も重い 1 本で全体の約半分、上位数個で 9 割近く。

直したのは 2 つ。サーバー側の N+1 で返却ドキュメント 8 割以上減、チャットの購読を直近数十件に絞って約 7 割減。6〜9 月の 3 か月で読み取り課金はおよそ半分。罠は監査ログ自体で 1 日約 170GiB。ログバケットに入れると 50GiB の無料枠超過が $0.50/GiB で月約 $2,500 になるため、_Default シンクから除外し BigQuery シンク（200MiB あたり $0.01）だけに流す。含意: 内訳を数えてから最重量の 1 本を直す。Web SDK の getDocs も監査ログでは Listen。寄与は未分離。

試すなら: Google Cloud コンソールの「IAM と管理 → 監査ログ」で「Firestore/Datastore API」の「データ読み取り」「データ書き込み」をオン → gcloud logging sinks create fs-audit bigquery.googleapis.com/projects/<PROJECT_ID>/datasets/<DATASET> --log-filter='protoPayload.serviceName="firestore.googleapis.com"'（データセットは先に作る）→ 同時に gcloud logging sinks update _Default --add-exclusion=name=exclude-fs-dataaccess,filter='resource.type="audited_resource" AND resource.labels.service="firestore.googleapis.com"' で既定のログバケットから外す → 1 日分を protopayload_auditlog.methodName・numResponseItems・callerSuppliedUserAgent で GROUP BY し、上位 1 本から直す（Listen が DATA_READ であることと protoPayload.serviceName のフィルタは Firestore の audit-logging ページ、「リアルタイムリスナーは含まれない」は query-insights ページ、--add-exclusion と sinks create は gcloud リファレンスで確認。金額と除外フィルタは記事）。

「止まってよいか」を prompt 型の Stop フックに判定させたら、10 日で 1,069 回中 488 回（45.7%）が差し戻し — 正しい停止も「止めてよい証拠がない」で止められる。連続の差し戻しは既定 8 回で打ち切り（CLAUDE_CODE_STOP_HOOK_BLOCK_CAP）

— 10/6 既報の /goal は prompt 型 Stop フックの包み紙。終わりの判定を LLM に任せたときの誤差し戻し率の実測で、条件の書き方を直す材料。

イサン氏（10/7）。~/.claude/settings.json の Stop に "type": "prompt"（timeout 30）で禁止状態 6 種を判定させた結果、1,069 回中 488 回を差し戻し、10 分で 30 回連続もあった。採点できた 13 件で正しい判定は 0。著者の推測は、判定役が会話に「止めてよい証拠」を探し、無ければ差し戻す側に倒れる。対策は、止める条件より先に「通す条件」を会話に残る証拠の形で書くこと。含意: /goal の条件にも確かめ方を書く。n=1、採点は差し戻された側が書いた。

試すなら: Stop フックや /goal の条件に「テストの出力に passed が含まれる」のような会話に残る証拠で「通す条件」を先に書く → 連続差し戻しの上限は既定 8 回なので、暴走が怖ければ CLAUDE_CODE_STOP_HOOK_BLOCK_CAP=2 のように下げて起動する → 差し戻し率は ~/.claude/projects/**/*.jsonl の Stop フック結果を数えて 1 週間見る（prompt 型フックと timeout 既定 30 秒は docs/en/hooks、8 回の上限と環境変数は v2.1.143 のリリースノート、数字は記事）。
