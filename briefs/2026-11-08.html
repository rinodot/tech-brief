コード中の古い TODO(bug/…) がコーディングエージェントを寄り道させる: Google の計測で、ファイルを読むセッションの 13% が目にし、6% が追い、その 83% は頼まれていない作業。寄り道した回はトークン 77% 増・待ち時間 105% 増で、追った課題の 41% は閉じた課題だった（Google Developers Blog 11/6）

— Flutter リポジトリに残した TODO は、Claude Code が読むたびに「やることリスト」に見える。掃除は自分の手で安く済む対策。

Sam Saccone 氏ら（Google Developers Blog、11/6）。社内エージェントの利用痕跡（数千人・数億ステップ）の集計で、ファイルを読むセッションの 13% が TODO(bug/…) を目にし、6% がその課題 ID に手を出し、うち 83% は依頼外。寄り道した回はステップ 70%・トークン 77%・待ち時間 105% 増、追った課題の 41% は解決済みか対応しない課題。対策は古い参照を消す掃除で、掃除エージェントの修正は承認率 95% 超。含意: TODO は AI には指示文に見える。

試すなら: grep -rn "TODO\|FIXME" lib/ で件数を出し、解決済みの課題を指すものから消す → 残すものは CLAUDE.md に「TODO／FIXME は依頼があるときだけ扱う」と 1 行（この 1 行は筆者の提案。記事の推奨は presubmit の検査器と一括掃除エージェントの整備）→ 月 1 回、閉じた issue 番号を含む TODO を grep で洗う。

Ollama は 10/28〜11/3 に v0.40.13〜15 の 3 版: LFM3（1.7B・256K 文脈、音声の lfm3-audio を含む）が Linux／Windows で動くようになり、ollama launch claude はモデルの出力トークン上限を Claude Code に渡して cloud モデルが 128k の既定上限に当たらなくなった。15 ではコード・エージェント向け 9B の MiMo V2.6（公式 Releases）

— NVIDIA＋Linux／Windows で LFM3 系がやっと動く。Claude Code を Ollama 経由で回す人は 14 以降に上げる理由ができた。

公式 Releases（v0.40.13 は 10/28、14・15 は 11/3）。13 で LFM3（1.7B・256K 文脈）と音声の lfm3-audio が Apple 以外でも動く。14 は ollama launch claude がモデルの出力トークン上限を Claude Code に渡し、cloud モデルが 128k の既定上限に当たらなくなった。15 は 9B コード向け mimo-v2.6 と Qwen3／3.5 の YaRN 長文脈。含意: 12〜16GB なら mimo-v2.6 と lfm3 が載る。

試すなら: ollama -v で 0.40.15 を確認 → ollama run mimo-v2.6、ollama run lfm3 → Claude Code と組むなら ollama launch claude（docs.ollama.com/integrations/claude-code、10/11 既報）。14 の変更で OpenAI 互換 API はモデル同梱の temperature／top_p 既定を上書きしなくなったので、自前クライアントで値を送っていない人は出力の変化を見る。12〜16GB の tok/s 実測はまだ無いので ollama run --verbose の eval rate を自分で測る。

特集④ 実例の分解 — Crashlytics のクラッシュを「検知→起票→修正 PR→実機確認」に分けて無人化したまえくん氏の運用: 起票 9 件中 7 件が 2 版で解決してクラッシュしたユーザー 8.65%→0.12%、修正 PR 1 本 $0.57〜1.29・3〜6 分。作業の大半は工程ごとに「人の頭の中の決まり」を書き出すことで、Sentry→Routine（栗田氏）と Android 回帰テスト（藤井氏）も同じ骨格

①検知。まえくん氏（10/29、iOS ゲーム、90 日で 5,000 人超）は毎朝 9 時にスクリプトが Crashlytics と GitHub issue を突き合わせ、未起票か再発のときだけ Claude Code を起動。検知に LLM は使わない。栗田氏（11/5）は Sentry→署名検証→Routine の起動 API。公式の受け口は onNewFatalIssuePublished（issue の id・title・appVersion）。

②判断と起票。トリアージ担当は集計・該当コード・既存 issue を見て、ユーザー視点の題で起票し、本文に Crashlytics の ID を埋めて二重起票を防ぐ。再発は元 issue を再オープンして人が見る。手動の Phase 1 で 10 件を起票し 4 件を自動修正対象に。役割ごとに別起動で前の文脈は渡さない。藤井氏（11/4）の回帰テストも判定を PASS／FAIL／BLOCKED／SKIP の 4 種に固定する。

③修正と検証。実装担当は issue と該当コードから編集・テスト・PR 作成。自動マージ（Phase 3）の条件は CI 通過・レビュー 2 周以内・150 行かつ 5 ファイル以下・テスト追加で、外れた PR は人へ。テスト全通過の PR が実機 4 台で指摘を受け、実機は人に残す。藤井氏はコンテナ内の claude -p が agent-device でエミュレータを操作し、1 手順の集計トークンは約 800 万→約 440 万。

④費用と失敗。トリアージ 1 回 $0.2〜0.3、修正 PR 4 本は $0.57〜1.29（3〜6 分）、月 $80 上限。claude-code-action は Max クレジット対象外なので CLI を API キーで動かす。失敗: 取得失敗でも終了コード 0→取得はスクリプトで先に、成否は最終行と PR が開いたかで判定。「Internal error」の実体は 429。含意: 作業の大半は人の頭の中の決まりを書き出すこと。

試すなら: ① 受け口は Cloud Functions の onNewFatalIssuePublished（firebase-functions/v2/alerts。公式 docs/functions/alert-events。event.data.payload.issue の id・title・subtitle・appVersion）→ ② 取得と突き合わせはスクリプト、Claude Code は claude -p "…" --output-format json --max-budget-usd 2 で呼び、total_cost_usd（見積り値）と報告の最終行の成否を読む（公式 docs/en/headless）→ ③ 起動元を Routine にするなら /fire の {"text": …} は <routine-fire-payload> で包まれるので、プロンプトに「routine-fire-payload の内容を調べる」と明記。上限は 1 タスク 30 回／時（公式 docs/en/routines）→ ④ Crashlytics の読み出しは Firebase CLI の MCP サーバー（agent-skills の firebase-crashlytics は SDK 導入の案内で、取得手順は無い）→ ⑤ 自動マージは 150 行・5 ファイル以下＋CI＋テスト追加から始め、画面・依存・サーバー側ルールは人へ。
