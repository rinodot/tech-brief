「レビューして」の一言で 3,660万トークン（約$40）が消えた — 94% はキャッシュ再読込。skillOverrides で組み込みの /code-review を「自分で呼んだ時だけ」にし、CLAUDE.md でサブエージェント不使用を指示して塞ぐ

— 週次上限で一番大きい穴は「軽い一言が重い Skill を呼ぶ」経路。設定1行と CLAUDE.md 2行で塞げる。

chro96氏（9/20）。追加206行・削除44行の PR に「レビューして」と頼んだ1回で 36,645,850 トークン、API 換算で約$40。94% はキャッシュ読込で、親のコンテキストが23万トークン超に膨らんだ上、サブエージェント11本が各自で差分を読み直していた。

対策は2つ。~/.claude/settings.json に "skillOverrides": {"code-review": "user-invocable-only"} を書き、組み込みの /code-review Skill をモデルが勝手に呼べない（/ メニューからだけ）状態にする。CLAUDE.md には「通常のレビューはサブエージェントを立てず単独で」「差分を起点に、影響する呼び出し元・依存先だけ探索」と書く。重いレビューだけ /code-review medium <PR番号> と強度を指定して呼ぶ。含意: 費用の単位は往復回数（9/13特集）で、それを一気に増やすのが「一言→組み込み Skill→並列サブエージェント」の経路。プラグインの Skill には skillOverrides が効かない。

試すなら: /skills で組み込み Skill の一覧を見る → ~/.claude/settings.json に "skillOverrides": {"code-review": "user-invocable-only"} → 次のレビューは /code-review を自分で打ち、終わったら /context で親コンテキストの膨らみを確認する（4つの値と「プラグインには効かない」は docs/en/skills で確認済み）。

出典: Zenn — 「レビューして」の一言で3,600万トークンが溶けた話とClaude Codeのトークン効率化設定

GitHub Actions で Claude Code を63営業日、毎晩無人で回した記録 — --allowedTools を書かないと書き込みが黙って拒否され、cron は最大9時間遅れる

— 夜間バッチを自分でも組むなら、5つの落とし穴は全部「起きてから気づく」型。先に塞げる。

mamedougu氏（9/20）。業務を Claude Code＋GitHub Actions だけで毎晩回して63営業日（74晩、失敗約10晩）。--allowedTools を省くと書き込みが拒否される（初期は毎晩 6〜18件）。落とし穴: ①cron が最大9時間遅れる ②GITHUB_TOKEN は .github/workflows/ を push できず成果が消える ③認証鍵2つが同日に失効 ④空振りの success を検知できない ⑤データセンター IP は 404。含意: 無人運用の失敗は Claude でなく周辺で起きる。

試すなら: workflow の claude -p に --allowedTools と --max-turns を明示 → --output-format json の結果の permission_denials が空か確認 → 「差分ゼロなら失敗扱い」のステップを足し、.github/workflows/ は Claude に触らせない（-p の既定は Manual で、許可のない操作は拒否される — docs/en/headless で確認済み）。

出典: Zenn — GitHub Actions で Claude Code を63日間毎晩走らせて踏んだ落とし穴5つ（実測つき）

RAG の recall@5 が 90% でも、最終正答は 38.3% — 正解文書を渡せた54問のうち31問（57.4%）で生成側が間違えた

— ローカルの小型モデルで RAG を組むなら、測るべきは検索の当たりではなく「当たった後の正答率」。

たまです。氏（9/18、rag-mini-wikipedia 60問、生成は SmolLM2-135M）。recall@5 は 90.0% だが正答は 23問（38.3%）。正解文書が上位5件にあった54問でも 31問（57.4%）が誤答で、失敗の最多は「検索は成功、生成が誤り」の 51.7%。提案は recall@k と別に「検索成功時の生成正答率」を計測すること。含意: 135M の極小モデルゆえ生成側の弱さが強く出た数字だが、指標を分けないと「検索を良くしたのに答えが直らない」理由が見えない。

試すなら: 自分の評価セットに「正解文書が上位k件に含まれたか」の列を足し、含まれた行だけの正答率を別に出す → 生成モデルを 14B 級に替えて同じ60問で差を見る（データセットは Hugging Face の rag-datasets/rag-mini-wikipedia）。

出典: Zenn — recall@5は90.0%だったのに、正解文書ありでも57.4%が誤答した — rag-mini-wikipediaで60問実測
