cron の claude -p "ok" が 1 回 39,968 トークン: --safe-mode（CLAUDE.md・フック・MCP を読まない）で −58%、--tools "" で −93%、--system-prompt の置き換えで 737 トークン（−98%）、--effort low で思考 102→0。公式 CLI リファレンスの裏取り: --safe-mode はトラブルシュート用、スクリプト向けの --bare はサブスクの OAuth では認証エラー（yosiki 氏、10/21）

— 無人の claude -p は、プロジェクトの文脈が要らない仕事でも CLAUDE.md とフックの固定費を毎回払う。自分の設定を厚くするほど、その固定費が黙って増える。

yosiki 氏（10/21）。認証切れの確認に定期的に撃っていた claude -p "ok" が、毎回 CLAUDE.md・フックの注入・MCP・全ツール定義を読み込んで 39,968 トークン（haiku）。--settings '{}' は 0%、--safe-mode で 16,798（−58%）、さらに --tools "" で 2,931（−93%）、--system-prompt "Reply with exactly: OK" で 737（−98%、約 54 分の 1）。1 日 4 回なら週 112 万→2 万トークン。

差分からの内訳は CLAUDE.md・フック・MCP が約 23,000、組み込みツール定義が約 13,900、既定のシステムプロンプトが約 2,200。個人用 CLAUDE.md は約 2.8 万字で、7 月の 37,994 から 3 か月で約 2,000 増えていた。出力側も --effort low で思考 102→0 トークン。含意: CLAUDE.md やフックを厚くするほど、それを使わない自動化の固定費まで一律に上がる。無人ジョブは「読ませない起動」に分ける。各条件 1 回、macOS・2.1.295。

試すなら: まず claude -p "ok" --output-format json < /dev/null | jq '.usage | .input_tokens + .cache_creation_input_tokens + .cache_read_input_tokens' で自分の固定費を測る → 文脈の要らない無人ジョブは記事の最終形 claude -p "ok" --model haiku --safe-mode --tools "" --system-prompt "Reply with exactly: OK" --effort low --no-session-persistence < /dev/null（< /dev/null が無いと 3 秒待って警告が出る）→ 公式 CLI リファレンスの位置づけ: --safe-mode は「壊れた設定のトラブルシュート用」で CLAUDE.md・skills・plugins・hooks・MCP・auto memory を読まず、認証・モデル・組み込みツール・権限は通常どおり（CLAUDE_CODE_SAFE_MODE が立つ）。--tools "" は組み込みツールだけで MCP には効かない（MCP も外すなら --disallowedTools "mcp__*"）。--system-prompt は安全指示ごと置き換わるので返答の形が決まった用途だけ → 公式が「スクリプト向けの最小モード」とする --bare は、記事ではサブスクの OAuth で認証エラー（claude --help では API キーか apiKeyHelper のみ）。サブスクの利用枠がキャッシュ読みをどう数えるかは記事も未確認なので、節約の実感は /usage で見る。

VRAM からあふれた分の代償を同じモデルで実測: gemma4 12B q8_0（13.1GB）は全部 GPU で 40.5〜43.5 tok/s、76% しか載らない 12GB 相当で 17.2、50% の 8GB 相当で 8.2、CPU のみ 4.6。ollama ps の PROCESSOR 欄が「100% GPU」かどうかが分かれ目（shacikku3 氏、10/21）

— 12〜16GB で「少し大きいモデル」を選ぶときの判断材料。あふれ方と速度の関係が 1 本のモデルで並んでいる。

shacikku3 氏（10/21）。RTX 4080 の VRAM を絞り、同じ gemma4:12b-it-q8_0 の生成速度を比べた。全部 GPU で 40.5〜43.5 tok/s、12GB 相当（約 76% が GPU）で 17.2、8GB 相当（約 50%）で 8.2、CPU のみ 4.6。4 分の 3 が載っても速度は半分以下。含意: 全部載る量子化と文脈長を選び、ollama ps の PROCESSOR 欄を先に見る。MoE はあふれても 64k で約 88 tok/s と注記、別に測る。模擬、Ollama 0.32.6、各 1〜2 回。

試すなら: ollama ps の PROCESSOR 列を見る（100% GPU なら全部載っている。39%/61% CPU/GPU のように出たらあふれ）→ あふれていたら量子化を 1 段落とす（q8_0→q4_K_M）か文脈長を下げて 100% GPU に戻し、ollama run <model> --verbose の eval rate で前後を比べる → 10/20 の OLLAMA_CONTEXT_LENGTH=64000 と組むなら、伸ばしたあとにもう一度 ollama ps（長文脈ほど CPU 側に押し出される。記事は文脈 65536＋補完用 1.1GB モデル同時で 43%/57%）→ MoE（LLM-jp-4.1 32B-A3B など）は 10/19 の --n-cpu-moe のとおり、あふれても遅くなりにくいので dense と分けて測る。
