無人の claude -p の記録上のコストを 48% 減らした 2 つの設定 — キャッシュ TTL を 5 分に（CLAUDE_CODE_PROMPT_CACHE_TTL=5m）、起動時に読むユーザー設定・MCP・スキル・自動メモリを外す（--setting-sources project,local --strict-mcp-config --disable-slash-commands と CLAUDE_CODE_DISABLE_AUTO_MEMORY=1）。koki_n22 氏の実測: 1 時間保持のキャッシュ書き込みが費用の 66.2%、$8.09→$4.22、テスト 17/17 は変わらず

— 9/30 既報の TTL（サブスク 1h・API キー 5m）と 10/8 既報の起動時の一覧を、無人の claude -p で同時に効かせた実測。10/5 既報の毎時ループの固定費を下げる具体策。

koki_n22 氏（10/11）。Kotlin の小さなライブラリを 4 タスクに分け、無人の claude -p で実装させた記録 543 ステップ・計 $277.31 を集計すると、費用の 66.2% が 1 時間保持のキャッシュ書き込みだった。1 時間保持の書き込みは通常入力の 2 倍、5 分保持は 1.25 倍。そこで TTL を 5 分にし、起動時に読むユーザー設定・MCP・スキル・自動メモリを外すと、同じ仕様・同じ Opus 5.5 で全実行 $8.09→$4.22（48% 減）。採点テスト 17/17 とマージ 4/4 は前後で同じ、起動時コンテキストは約 32.3k→約 9.3k トークン。

5 分保持で足りるのは、無人実行はターンの間隔が短く失効しないから（変更後の API 外の待ちは最大 80 秒。732 秒待った別の回は失効した可能性が高い）。--bare は同じ省略を一度にやるがサブスクのログインを使えない（9/24 既報）ので、サブスクならこのフラグ群になる。含意: 無人ループの固定費は TTL と起動時の読み込みで半分にできる。注意: 前後各 1 回でターン数も 190→163 と減っており、ドル額は API 換算で請求額ではなく、使用枠への影響と処理時間は未計測。

試すなら: いつもの無人タスク 1 本を CLAUDE_CODE_PROMPT_CACHE_TTL=5m CLAUDE_CODE_DISABLE_AUTO_MEMORY=1 claude -p "…" --setting-sources project,local --strict-mcp-config --disable-slash-commands --tools Read,Grep,Glob --effort high --output-format json | jq '.total_cost_usd' で前後 3 回ずつ回し、費用と成果物を比べる（--effort はユーザー設定を外すと既定に戻るので明示）→ 起動時の読み込みは /context で前後を見る → 長いビルドやテストで待ちが 5 分を超える工程があるなら、その工程だけ 1h に戻して比べる（変数は docs/en/env-vars: 5m／1h のみ、v2.1.242 以降、promptCacheTtl 設定より優先。フラグは docs/en/cli-reference。--bare が API キー課金になる点は docs/en/headless）。

RAG で質問文の「確認」が正解を押し出していた — 字句検索の多出語を文書頻度（DF）12 で足切りしたら 10 ケースの正解到達が 28→31 件（tom 氏）。重みを下げる案は逆効果、RRF は同じ id が両方の表に出ると点が足される

— 10/3 既報の Pi 上ハイブリッド RAG や 10/5 既報の grep と埋め込みの併用で起きる典型的な事故。日本語で字句検索を足すなら、先に語ごとの DF を見る理由。

tom 氏（tomtom55555、10/11）。承認済み 144 件の記録を引く RAG で、質問文の「確認」が字句検索で 17 行に当たり、RRF（k=60。同じ id が両方の表に出ると点が足される）の上位を埋めて、意味検索 3 位の正解が採用枠 18 件から落ちた。字句の重みを 0.4 に下げると 9 ケースで 27→25 件と悪化。文書頻度（DF）が 12 を超える語を字句照合から外すと、10 ケースの正解到達は 28→31 件。含意: 日本語の字句検索は多出語を外してから足す。閾値は絶対件数なので記録が増えたら見直す。小規模。

試すなら: 自分の RAG の評価質問 10 問で、質問を 2 文字以上の語に割り、語ごとの DF を SELECT count(*) FROM chunks WHERE text LIKE '%語%' で数える → DF が上位の語を字句照合から外す閾値を「なし／12／6」の 3 段で比べ、正解到達数が増えた閾値を採る → 閾値は件数で固定せず、評価のたびにコーパス件数と語ごとの DF を表示して、両者が近づいたら相対値（コーパス比）に切り替える（数字と式は記事。DF を数える式と候補を拾う式は同じ関数にまとめる、が記事の要点）。

16GB の GPU でローカルのエージェントが止まる 2 つの理由 — Ollama の既定 num_ctx 4096 に system prompt の 18k トークンが入らず HTTP 400、会話が上手いモデルがツールを呼ばない。ぷゆるる氏が RTX 5070 Ti＋Hermes Agent で踏んだ順と直し方

— 10/11 既報「Claude Code を手元の Ollama で」の条件（tools 対応・64k 以上）を、同じ 16GB 級の GPU で踏み外すと何が起きるかの実例。

ぷゆるる氏（10/11）。RTX 5070 Ti 16GB で Hermes Agent v0.19.0（Ollama）を動かすと、gemma4:12b はツールを呼ばず、Ornith-1.0-9B では初回の 18,358 トークンが既定の 4096 を超えて HTTP 400。Hermes 側は上限 262,144 を信じるので、Modelfile の PARAMETER num_ctx 65536 の派生モデルを作り、Hermes の context_length も揃えた。含意: 文脈長とツール呼び出しの最小テストを先に通す。試行は少数。

試すなら: Ollama を OLLAMA_CONTEXT_LENGTH=65536 で起動するか、モデルごとに FROM <model>＋PARAMETER num_ctx 65536 の Modelfile から ollama create <name>-64k -f Modelfile → 本番のタスクの前に「ls を 1 回呼ぶ」「ファイルを 1 つ読んで要約」の 2 問でツール呼び出しが起きるかを見る → ollama ps と nvidia-smi で GPU に載っているか確かめる（Claude Code 側は 10/11 既報の ollama launch claude が v0.40.2 からモデルの最大文脈長で起動するので、この罠は settings.json の env で自前接続するときに踏む。OLLAMA_CONTEXT_LENGTH は docs.ollama.com/faq、num_ctx は docs.ollama.com/modelfile）。

出典: Zenn — 16GB VRAM で Hermes Agent をローカル LLM で動かす — tool-calling で詰まった3点
