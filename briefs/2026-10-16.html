Claude Code の費用（API 換算）の 97.9% は「キャッシュの読み直し」— 97 セッション・21,095 リクエストの集計。効いたのは ①終わったら /clear・途中は /compact（13 回で約 $330）②大きいファイルはサブエージェントに読ませる（CLAUDE.md の一行で 0 回→82 回）③独立したツール呼び出しは 1 応答にまとめる（約 22% 減）。「毎回読むファイルを短くする」は −0.5% で効かなかった（r.iguchi 氏）

— 10/12 既報「TTL 5 分と起動の固定費」と昨日のアイドル compact を、自分のログで裏付ける方法。費用の正体が「文脈の大きさ×往復数」なら、節約は設定より運用の型で決まる。

r.iguchi 氏（ムクイル、10/15）。対策前の 97 セッション・21,095 リクエストでは、入力トークンの 97.9% がキャッシュ読み取り。1 往復の費用は会話の長さで 30 倍以上開き、最悪は 1 会話を 13 日・5,065 リクエスト。①終わったら /clear、途中は /compact。手動 compact で会話は平均約 8 分の 1、13 回で少なくとも約 $330。②大きいファイルはサブエージェント（Read・Grep・Glob、sonnet）に読ませる。対策前 0 回が、CLAUDE.md の一行「大きいファイルはサブエージェントで読む（常に守る。頼まれるのを待たない）」で、以後 7,427 リクエスト中 82 回に。

③ツールを呼んだ応答の 84.2% が 1 つだけ。「関係のない呼び出しは 1 回の応答にまとめる」で平均 1.17→1.50 個、リクエスト約 22% 減。含意: 読み直し費用は文脈の大きさ×往復数。固定費より往復数と会話の長さを減らす方が桁で効く。注意: 個人のログ、API 換算（読み取り $0.50/M の仮定）、前後でモデルも変わり③はルールだけの効果と言えない、compact の額は下限。

試すなら: 記事付録の cc_usage.py を保存して CACHE_READ_PRICE=0.5 python cc_usage.py（Windows は PYTHONIOENCODING=utf-8 を前置）で ~/.claude/projects/<プロジェクト>/<セッションID>.jsonl を集計し、キャッシュ読み取りの割合と長く続いた会話を確認 → .claude/agents/code-explorer.md を name: code-explorer／tools: Read, Grep, Glob／model: sonnet で作る → CLAUDE.md に「作業が終わったら /clear」「大きいファイルはサブエージェントで読む（常に守る。頼まれるのを待たない）」「関係のないツール呼び出しは 1 回の応答にまとめる」の 3 行 → 1 週間後に同じスクリプトで再集計（単価は公式料金表で差し替え。昨日のアイドル compact は放置時の保険、/clear は能動の節約）。

ローカル LLM の喋り出しが遅い原因は「プロンプトの順序」— 毎回変わる部分より前に固定の約 2,000 トークンを置き直しただけで、再 prefill 2,067→約 180〜240 トークン、TTFT 約 10.7 秒→約 1.7〜2.2 秒（M3 16GB・mlx_lm.server）。生成速度は約 18 tok/s のまま（OEC-7m 氏）

— 10/9 既報の KV キャッシュ・10/12 既報の TTL と同じ「接頭辞が一致した分だけ省ける」原理をローカルで。llama-server も既定でプロンプトキャッシュが有効なので、順序の見直しだけで効く。

オーイーシー OEC-7m 氏（10/14）。ロボット対話の喋り出し約 10.7 秒の原因は組み立て順。毎回変わる場所一覧・想起メモリの後ろに約 2,000 トークンのマニュアルがあり、キャッシュに当たらず毎回 prefill されていた。マニュアルを固定ルールの直後へ上げただけで、再 prefill 2,067→約 180〜240 トークン、TTFT 約 1.7〜2.2 秒。同じ質問の連投では差が消え、著者も一度「効果なし」と誤判定。含意: 変わらないものを前、変わるものを後ろ。M3 16GB・MLX の 1 台、モデル名なし。

試すなら: 組み立て順を「システム規則→大きな固定資料（マニュアル・few-shot）→検索結果など毎回変わる部分→履歴→今回の発話」に並べ替える → llama-server はプロンプトキャッシュが既定で有効（無効化は --no-cache-prompt）なので、別々の質問を続けて投げ、"stream": true, "return_progress": true を付けたリクエストの prompt_progress で cache（再利用できたトークン）と processed（prefill したトークン）を比べる → 同じ質問の連投で測らない → 中間だけ変わる構成なら --cache-reuse 256（既定 0。一致しない部分を KV シフトで飛ばして再利用）も試す（フラグは llama.cpp tools/server/README）。

出典: Qiita — ローカル LLM が遅い原因は、モデルでもエンジンでもなく「プロンプトの順序」だった
