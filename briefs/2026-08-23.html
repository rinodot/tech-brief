MCP公式ロードマップ公開 — ポーリング前提をやめ、サーバーから通知する設計へ

— 自作MCPサーバーの前提が半年〜1年で変わる。今の書き方の寿命が読める話。

8/22、MCP（Model Context Protocol、AIエージェントに外部ツールをつなぐ共通規格）のコアメンテナ2人が今後の優先5分野を公式ブログで公開した。核はエージェント間メッセージングの刷新で、クライアントが定期的に問い合わせるポーリング前提をやめ、サーバー側から発火するイベント（webhookやチャネル）へ寄せる。長時間タスクを扱うTasks拡張（SEP-2663）も正式仕様への格上げを目指す。伝送路は7/28版仕様を土台に、ローカルの「Streamable HTTP over stdio」とリモートHTTPを一本化。認可はDPoP（トークンに鍵の所持証明を添える方式。盗まれたトークン単体では使えなくなる）の採用が確定し、サブエージェントへの権限委任シナリオまで想定に入った。

含意: 効くのは①と④だ。ポーリングで書いた箇所は通知型に寄せる余地があり、④はツールを増やすほど一覧そのものが文脈コストになるという指摘。今日の特集で扱うSkillsの3段階ロードと同じ発想で、「必要になるまで読ませない」が界隈全体の設計方針になりつつある。

出典: MCP公式ブログ

753BのMoEをGPU 1枚で動かす論文 — 帯域に合わせて実行を組み替える

— 「16GBで27B」という今の天井を、量子化とは別の角度から押し上げる手法。

MoE（専門家を切り替えて一部だけ動かす方式）推論の論文「FreeToken」が8/22にHNで浮上した（arXiv提出は8/17の拾い上げ。著者にUC BerkeleyのIon Stoica）。エキスパートの配置・CPU/GPU分担・状態の再利用を帯域に合わせて動的に組み替える手法で、実装はGitHubで公開済み。著者のX投稿ではGLM-5.2 753BをRTX PRO 6000で15 tok/sとあるが未検証。含意: MoEは帯域律速。量子化で削らずとも置き場所の設計で実効速度が変わる。

特集: Skillsを自作して動かす — 3段階ロードの原理と最短手順

Skills（Claudeに手順書を渡す仕組み）が節約になる理由は、全部を一度に読まないからだ。起動時にシステムプロンプトへ常駐するのは、全スキルのnameとdescriptionだけ。発話がdescriptionに合致して初めて、ClaudeがBashでSKILL.md本体をcatして読む。参照先の追加ファイルは、必要と判断したときだけ開く。この3段構えのおかげで、スキルに書ける分量は実質的に上限がない。目次→章→付録の順に読む本と同じ構造だ。

手順は短い。~/.claude/skills/<名前>/SKILL.mdを作り、フロントマターにnameとdescriptionを書く。nameは小文字とハイフンのみ64字以内、processing-pdfsのような動名詞形が推奨。descriptionは三人称で「何をするか」と「いつ使うか」の両方を書き、具体的なキーワードを入れる。「Helps with documents」のような曖昧な記述はトリガーしない。本体は500行未満に収め、超えるなら別ファイルへ逃がす。置き場所は~/.claude/skills/が全プロジェクト、.claude/skills/がそのプロジェクトのみ。

落とし穴が3つある。第一に、フロントマターのYAMLが壊れていてもエラーにならず空メタデータで読み込まれる。/スキル名で手動起動はできるのに自動で起動しない、という症状になる。第二に、allowed-toolsは禁止機能ではない。確認プロンプトを省くホワイトリストにすぎず、指定外のツールも呼ばれる。禁止はdisallowed-toolsの側だ。第三に、スキルが増えるとdescriptionは文脈窓1%の予算に収まるよう自動で切り詰められ、使用頻度の低いものから記述が落ちる。「急にトリガーしなくなった」はこれが原因のことがある。/contextで消費量が見える。

出典: Claude Code ドキュメント（Skills）
