Android 17、アプリ毎のメモリ上限を全RAM帯へ拡大 — 落とされる前に監視を

— きょうPixel 11発売でAndroid 17実機が増える。画像多めのFlutterアプリはまさに対象。

Googleが8/19、Android 17の「アプリ単位メモリ上限」を4GB〜16GB超の全RAM帯へ広げると開発者ブログで告知した。仕組みは段階制で、上限を超えたアプリはまずメモリページがzRAM（RAM上の圧縮領域）へ退避されて動作が重くなり、それでも増え続けるとシステムに強制終了される。終了理由はApplicationExitInfo.getDescription()が返す「MemoryLimiter:AnonSwap」で判別できる。監視はAndroid Vitalsの「Memory Usage」「Bitmap Memory Usage」指標と、OOM追跡を強化したCrashlytics 20.1.0以降が推奨とされた。

6月の導入時は「極端なリークを狙う控えめな運用」とされていたが、今回は適用拡大の予告で、きょう8/20にはAndroid 17搭載Pixel 11の店頭販売も始まる。含意: 画像を多く扱うFlutterアプリはBitmap指標の監視対象そのもの。Crashlyticsのバージョン確認と終了理由のログ取得を今のうちに仕込んでおくと、「勝手に落ちる」報告を切り分けられる。

週次上限、8/19終了→8/31へ再延長 — 「恒久化したい」とAnthropic

— 昨日の「8/31で終了」の続報。実は締切はきのうで、土壇場で延びていた。

昨日「8/31で終了」と伝えたClaude Codeの週次上限50%増プロモは、正確には期限は8/19で、直前に8/31へ再延長されていた（昨日参照した文書は延長反映後。経緯を補正する）。公式は「恒久化したいが需要が強く容量が逼迫しうる」と表明、文書は依然「期間限定」のまま。延長は2度目。同日のv2.1.236はauto modeを強化し、Monitorルール経由の審査迂回と.env改名によるサンドボックス回避を塞いだ。含意: 次の判断日は8/31。`/usage`での消費把握の推奨は変わらない。

GitHub障害の全容判明 — 障害を10倍に増幅したのはVS Codeだった

— 月曜の7時間47分停止の続報。リトライ設計の教材として一級品。

原因分析が公開された。発端はIstio（通信仲介のサイドカー）の同時接続上限。自動スケールの監視対象から漏れていて増設されず、ロードバランサが枯渇した。さらに応答遅延でVS Codeの潜在リトライバグが発火し、Copilot認証への通信を約10倍に増幅、復旧を遅らせた。火曜のWiz対GitHub係争も、Wiz CTOが「co-author表記では帰属を判断できない」と認め、人間の記述で決着した。含意: 上限と指数バックオフの無いリトライは障害の増幅器。自作アプリのAPI呼び出し設計に直結する教訓だ。

出典: GitHub Status（RCA）
