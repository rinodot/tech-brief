git push を deny しても git -C . push は素通りする — deny は命令文字列との照合なので、PreToolUse フック（Python）で前置きと -C／-c を飛ばして subcommand を見る。"onFailure": "block"（v2.1.295）でフックが失敗しても止め、「止める形 22・通す形 7」のテストを先に作る（飯島紘一氏、Windows）

— 9/14 既報「deny の Write(パス) は参照されない」、10/11 既報「Write(...) は素通り」に続く deny の限界と、10/9 既報の onFailure: "block" を実際に使った設定例。

飯島紘一氏（k_iijima、10/12）。deny に Bash(git push *) と書いても、git -C . push、git -c push.default=current push、git 'push'、sh -c '…' は文字列が一致せず通る。そこで PreToolUse の Python フックが、命令を ;・&&・| で分け、env・sudo などの前置きと -C／-c を飛ばして subcommand を見る。bash -c と $( ) の中身も同じ手順で読み、読めない命令は "git" を含むだけで止める（終了コード 2）。

要点は 2 つ。"onFailure": "block"（v2.1.295 以降）で、フックが起動できない・時間切れでも命令を通さない（既定は素通り）。先に「止める形 22・通す形 7」のテストを作り、わざと壊して 5 個の抜けを見つけた。含意: deny は入口の網で、本当に止めたい操作は構文を読むフックと fail-closed の組で守る。限界: $( ) の入れ子・alias・PowerShell は読めず、settings もフックも AI が書き換えられるので著者は AI 専用の OS アカウントで分けた。Windows、n=1。

試すなら: .claude/settings.json の hooks.PreToolUse に {"matcher": "Bash", "hooks": [{"type": "command", "command": "python \"$CLAUDE_PROJECT_DIR/.claude/hooks/block_git.py\"", "onFailure": "block"}]} を置き、フックは stdin の JSON の tool_input.command を読んで、止めるときは stderr に理由・終了コード 2 → 先に git -C . push、sh -c 'git push'、$(echo git) push を含む「止める形」と git status・git log の「通す形」をテストに書く → フックをわざと exit 1 に壊して、それでも命令が止まることを確かめる（終了コード 2 の扱い・onFailure の値 continue／block と既定 continue・CLAUDE_PROJECT_DIR は docs/en/hooks。Bash(...) の deny が書かれた形にしか当たらない点は docs/en/permissions の bash-rule-limits）。

9/25 既報の三値 Bonsai 2 27B を RTX 4070 12GB で — PTQ1_0 は VRAM 7.6GB・56 tok/s（同じ 27B の Qwen3.8 Q4_K_M は層が溢れて 3.55）。ただし文脈 64K で 48.9→17.1 tok/s の崖があり、-fa on -ctk q8_0 -ctv q8_0 なら 128K でも 55.7（ローカルAIラボ氏）

— 10/4 特集③の KV キャッシュの式がそのまま速度に出た実測。12GB で長い文脈を使うときの既定値の罠と、回避の 1 行。

ローカルAIラボ氏（10/12、RTX 4070 12GB）。PrismML 版 llama.cpp で PTQ1_0（5.95GB）は 56.2 tok/s・VRAM 7,608 MiB、Qwen3.8-27B Q4_K_M は 3.55。だが KV が既定の 16bit だと PQ2_0 は 64K で 17.05 tok/s に落ち、エラーは出ない。-fa on -ctk q8_0 -ctv q8_0 なら PTQ1_0 は 128K でも 55.71。含意: 12GB では文脈長を先に決め、KV を 8bit にしてから崖を測る。1 環境・品質は未検証。

試すなら: 手持ちのモデルで llama-server -m <model>.gguf -ngl 99 -c 65536 -fa on -ctk q8_0 -ctv q8_0 --parallel 1 を起動し、8K／32K／64K の入力で tok/s を 3 回ずつ取って崖が消えるかを自分の GPU で見る → Bonsai 2 を試すなら PrismML-Eng/llama.cpp のリリース版と prism-ml/Ternary-Bonsai-2-27B-gguf の PTQ1_0 から（素の llama.cpp では動かない。9/25 既報）→ 思考を切るなら起動時に --chat-template-kwargs '{"enable_thinking": false}'（-fa・-ctk／-ctv（既定 f16）・--chat-template-kwargs・--reasoning-budget は llama.cpp の tools/server/README。8bit KV の品質差は未検証なので、評価セット 1 本で前後を比べてから常用）。

Flutter 3.47 で分かれた material_ui への移行は dart fix --apply --code=migrate_design_widgets で 14 ファイル 17 件が自動、手で直すのは 3 点（barrel の export、ローカライズの delegates、any のバージョン固定）。marwaMejri 氏の小さなアプリでテスト 10/10 は移行後も同じ

— 9/11 既報の material_ui 1.0.0 から 55 日で 7 リリース。自分のアプリを移すときの最短手順と、自動では直らない所。

marwaMejri 氏（dev.to、10/12、material_ui 1.6.0）。dart fix --dry-run --code=migrate_design_widgets で 14 ファイル 17 件が自動。残る手直しは 3 点: barrel の export（残ると既定色が紫にずれる）、ローカライズの delegates の置き換え（放置すると仏語テスト 3 件が落ちる）、any を ^1.6.0 に固定。含意: サードパーティ UI なしなら短時間、ThemeData を受け渡すパッケージは橋渡しでも救えない。n=1。

試すなら: ブランチを切って dart fix --dry-run --code=migrate_design_widgets で件数だけ見る → --apply 後に grep -rn "flutter/material.dart" lib/ で残った export 行を探し package:material_ui/material_ui.dart に書き換える → flutter test と、MaterialApp の localizationsDelegates が GlobalMaterialLocalizations.delegates（material_ui 版）になっているかを確認 → ThemeData を受け取るサードパーティ UI パッケージが 1 つでもあれば本番は待つ（手順と MaterialUiCompatibilityBridge は pub.dev/packages/material_ui の README。1.6.0 は 10/6 公開）。
