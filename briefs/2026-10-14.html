Flutter Web＋Firebase の AI 英会話を作り直し、原価を「1 人 月 20 円」に収めた費用設計 — 回数の上限・1 人 1 日 $0.02 の天井・無料枠全体で 1 日 $3 をすべて Cloud Functions 側で強制し、モデル名と max_tokens もサーバーで固定する（Wa-rp Studio 氏）

— 自分の Flutter／Firebase アプリに AI 機能を足すとき「どこで止めるか」を決める実例。中継先を Claude API に替えても形は同じ。

Wa-rp Studio 氏（10/13）。Flutter Web（PWA）＋Firebase Auth＋Cloud Functions（Node.js 22）が OpenAI を中継、課金は Stripe。AI 呼び出しは全部 Functions 経由で ID トークン必須、モデル名と max_tokens もサーバーで決める。原価は 1 回 会話 約 0.009 円・フィードバック 約 0.033 円・翻訳 約 0.008 円で、無料ユーザーが毎日上限（会話 10・ロールプレイ 15・翻訳 10・フィードバック 5）まで使っても月 約 18 円。

上限は回数と金額の二重で、1 人 1 日 $0.02、無料枠全体で 1 日 $3。原価は最悪でも月 約 1.35 万円で止まる。プロンプトは発話 16 件×3 回の固定セットで測り、4 文以上の長い返答 17%→2%、平均語数 14.6→11.9。Haiku 5.5 は同じ指示でトークン 1.7〜1.8 倍。広告は紹介サイトだけに置き、サブドメインを分ける（同一オリジンだと広告スクリプトが Firebase のログイン情報に届く）。含意: 回数・金額・モデルの 3 つをサーバーで強制し、クライアントは表示だけ。紹介記事で、月額は試算。

試すなら: AI 呼び出しを Cloud Functions の onCall に寄せ、request.auth が無ければ HttpsError（unauthenticated）で弾く → Firestore に usage/{uid}/{YYYYMMDD} の回数と金額を持ち、トランザクションで加算してから OpenAI／Claude を呼ぶ（上限超えなら呼ばずに返す） → モデル名・max_tokens は Functions の定数に置き、クライアントの引数から外す → 全体の 1 日予算はカウンタ 1 つで足りる（onCall・request.auth.uid・HttpsError は firebase.google.com/docs/functions/callable。広告を置くなら Auth を使うオリジンと分ける）。

30B クラスを 12GB で動かすなら、4bit を部分オフロードするより 2bit で全層を GPU に — Muse Glimmer 30B は 2bit 全層で 38 tok/s、4bit は 38/53 層で 3.7 tok/s。下書きモデル（DFlash）を足すと 4bit が 7.72 に、-ngl 34→36 でプロンプト処理が 6 分の 1 に落ちる崖（ローカルAIラボ氏）

— 10/13 既報の Bonsai 2 と同じ RTX 4070 で、量子化の選び方・崖の位置・投機デコードを 1 本で測った実測。

ローカルAIラボ氏（10/13、RTX 4070 12GB）。2bit（10.01GiB）は 53 層全部が GPU に載って 38.06 tok/s、4bit（Q4_K_M）は 38 層までで 3.70。2bit も 2 層を CPU に落とすと 24.78、4bit は 34→36 層でプロンプト処理が 438.9→68.4 tok/s に落ちる崖。DFlash 投機デコードで 4bit は 3.76→7.72（採用率 0.66）。品質は両方同等（地理は両方誤答）。含意: 12GB では全層が載る量子化を先に選び、崖は自分で測る。n=1。

試すなら: llama-server -m <2bit>.gguf -ngl all -c 8192 -fa on --jinja で起動し、llama-bench -m <model>.gguf -p 512 -n 128 で pp512／tg128 を取る → 載りきらないモデルは -ngl を 2 層ずつ減らして pp512 が急落する位置を控える → 下書きモデルがあるなら -md <draft>.gguf --spec-type draft-dflash --spec-draft-n-max 3 --spec-draft-ngl all を足し、ログの draft acceptance を見る（-ngl の all・-md・--spec-type・--spec-draft-n-max（既定 3）・--spec-draft-ngl は llama.cpp の tools/server/README。思考の強さは --chat-template-kwargs '{"reasoning_strength":"low"}' で、2bit は 718→317 トークン）。

cron の claude -p に書かせる文章は 7 日で 8 倍に伸びた（70→545 字）— 原因は前日の投稿を手本に読んでいたこと。守らせたのはプロンプトの上限ではなく、投稿前に件数と文字数を検証して超過なら投稿しないスクリプト（よだか氏の RSS→Discord 日報）

— 無人の claude -p を回す人向け。出力の形は LLM への指示でなく、後段の決定的なチェックで固定する。

よだか氏（10/13）。RSS から 5 本選んで Discord に流す日報を、スキル＋claude -p "/rss-digest" で cron 実行。文字数の指示は守られず、おすすめ理由は初日 70 字→7 日目 545 字。原因は前日の投稿を手本にしたこと。対策は投稿前の検証（件数＝itemCount、summary 80・comment 50・reason 100 字超なら投稿しない）と「前日の投稿を読まない」の追記で、以後 2 週間 超過なし。スキルは cwd 直下しか読まれず、cron の cwd がずれると動かない。

試すなら: git clone https://github.com/yodakaEngineer/rss-digest && cd rss-digest && cp config.example.yaml config.yaml で sources と limits を自分用に直し、claude -p "/rss-digest" を手で 1 回 → cron は cd /path/to/rss-digest && claude -p "/rss-digest"（cwd を必ず合わせる） → 自分の無人ジョブにも「件数が N・各項目の上限」を検証するスクリプトを LLM の後段に置き、違反なら終了コード 1 で送信を止める（itemCount・windowHours・limits は同リポジトリの config.example.yaml。10/1 既報の Stop フック（終わりの条件）と、この出力側の門を組み合わせる）。
