計画に入るかはモデル任せなので、CLAUDE.md に基準を書いて数えた。「新機能・複数ファイル・設計判断」「人が読む文書」は入る、「値や場所を聞く質問、1 か所の小さな修正」「計画承認後の実行」は入らない、迷ったら「文書なら入る」。文書・全工程の依頼 20 回は全部入り、質問・小修正 16 回は 1 回も入らなかった。基準を具体化すると調整に使った課題では 15/15 だが、別の課題では 11 回に下がった（元の基準は 12/12）。含意: 計画の費用は「文書の割合」で決まる。基準は手元の課題に合わせすぎない。コストは計算値、n は小さい。

試すなら: ~/.claude/settings.json に { "model": "opusplan" }（セッション内なら /model opusplan）→ CLAUDE.md に「## 計画モードの使い方」として「入る: 新しい機能の実装、複数のファイルにまたがる変更、設計の判断が絡む依頼。人が読む文書（要件定義、設計書、報告書）を書く依頼」「入らない: 値や場所を聞く質問、1か所の小さな修正。計画を承認した後の実行」「迷ったとき: 文書を書く依頼なら入る。それ以外は入らない」「計画に書くこと: 変更するファイルと手順、確かめ方。短くてかまわないが決める点は省かない」を書く → 1 週間、自分の依頼を「質問／小修正／実装／文書」に分けて計画モードに入った回数と /usage（API なら /cost）の減りを控える → README や設計メモのような小さな文書は /model sonnet で直接書かせる方が安い。

ローカル RAG（Ollama＋LlamaIndex、qwen3:14b＋bge-m3）で 13 問を設定ごとに測ると、効いたのは「256 トークン分割」「リランカーで 20 件→4 件」「思考オフ（21.0→4.3 秒）」の 3 つで、併用すると MRR 1.000・6.2 秒。効かなかったのは「資料にないことは答えない」の厳しい指示（正答率 0.923→0.769）と文脈長（3,900〜40,960 で精度は不変、メモリだけ 9.8→12GB）（岡山 勇治 氏、10/19）

— 日曜の特集で組んだ構成（チャンク・リランカー・評価）を、設定 1 つずつ変えて測った実測。「強く禁じる指示が精度を下げる」は自分の RAG プロンプトでも疑う価値がある。

岡山 勇治 氏（10/19、Mac）。社内文書 5 本・13 問で、基準（512 トークン分割・検索 4 件）は MRR 0.962・正答率 0.923。256 トークン分割で MRR 1.000、リランカー（20 件→4 件）で 1.000、思考オフで 4.3 秒、3 つ併用で 1.000・0.923・6.2 秒。「資料にないことは答えない」と強く書くと 0.769。ctx は 3,900〜40,960 で精度不変、検索 8 件とハイブリッドは 1 問だけ改善。含意: 効くのは分割・並べ直し・思考の 3 つ、禁止文は副作用を測ってから。各 1 回。

試すなら: 日曜の構成に 3 つ足す: チャンクを 256 トークン前後に → 検索 20 件→bge-reranker-v2-m3 で上位 4 件 → 生成は思考オフ（Ollama の /v1/chat/completions なら reasoning_effort: "none"。temperature=0 のまま思考 ON だと 1 問で 10 分固まることがある、と記事）→ 「資料にないことは答えない」を入れる前と後で同じ 13 問を採点し直す → ollama ps の CONTEXT 列で実際の文脈長を確認（LlamaIndex は未指定だとモデル最大の 40,960 を使っていた。公式 docs: VRAM 24GiB 未満の既定は 4k、エージェント用途は 64000 以上を推奨、OLLAMA_CONTEXT_LENGTH=64000 ollama serve。大きくするほどメモリが要るので PROCESSOR 列が 100% GPU のままか見る）。

— 自分の Play アプリの次回更新でそのまま使えるチェックリスト。16KB ページサイズ（Android 15 以上をターゲットにするアプリの要件）と R8 の release 限定の白画面は、debug では気づけない。

はんぺん 氏（10/17）。FFmpeg を外した arm64 release APK は 123,392,433→62,003,118 バイト。R8 の -keep のパッケージ名が typo で効かず、release だけ UnsatisfiedLinkError で白画面。debug は R8 を通さず気づけない。Data safety「収集なし」のため release マニフェストで INTERNET を外し、約 101〜128 秒の実行で送受信増分 0。含意: release 専用の検査を 1 本持つ。n=1、16KB の実行検証は一部未了。

試すなら: flutter build apk --release --target-platform android-arm64 → zipalign -c -P 16 -v 4 build/app/outputs/flutter-apk/app-release.apk（build-tools 35 以上。16KB は Android 15 以上をターゲットにするアプリの要件）→ 16KB システムイメージのエミュレータで adb shell getconf PAGE_SIZE が 16384 のまま主要画面を 1 周 → release ビルドだけ通る起動スモークテスト（最初のフレームでログを 1 行出し adb logcat で待つ。R8 の -keep は実際のパッケージ名を jar の中身で確かめる）→ 通信しないアプリなら android/app/src/release/AndroidManifest.xml に <uses-permission android:name="android.permission.INTERNET" tools:node="remove" /> を置き、adb shell dumpsys netstats で UID の送受信の増分を見る（Firebase を使うアプリには当然 INTERNET が要る）。
