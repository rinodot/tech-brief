Haiku 5.5 はどこで Opus 5.5 に負けるか、163 回の実測: 仕様が明確な課題（L2〜L5）は Haiku も全問満点、差が出たのは「報告に書かれていない境界ケース」を含む難しいバグ 1 件だけで、Sonnet 10 回中 8 回・Opus 6 回・Haiku 1 回。1 回あたりの費用は Haiku $0.026・Sonnet $0.19・Opus $0.45（Haiku は Opus より約 94% 安い）。テスト実行を許可すると通過数は変わらず、他の部分を壊した回数が 15 回中 2→0（yunany90 氏、10/24）

— 10/22 の「計画 Opus／実装 Sonnet」に、Haiku をどこまで下ろせるかの数字が足された。npm test を allow に入れる効果も測っている。

yunany90 氏（10/24）。Windows ノート 1 台で、Claude Code の Haiku 5.5・Sonnet 5.5・Opus 5.5（いずれも effort medium）に空フォルダから課題 L2〜L6 を解かせて計 163 回。隠しチェック 9〜38 件の L2〜L5 は 3 モデルとも全問満点。差が出たのは実在ライブラリ marked のバグ 3 件（L6）のうち、報告に書かれていないコードスパン内バッククォートの境界ケースで、7 件中 6 件を通したのが Sonnet 10 回中 8 回、Opus 6 回、Haiku 1 回。完全に直した実行はなし。

費用は全段階の 1 回平均で Haiku $0.026、Sonnet $0.19、Opus $0.45。テスト実行（node・npm test・読み取り専用 git。インストールと通信は禁止）を許可した 15 回では通過数は変わらず、テストなしで 2 回あった「他の部分を壊す」が 0 回になった。含意: 仕様がテストで書けている仕事は Haiku のサブエージェントで足り、Opus は「仕様に無い境界」を疑う役に絞る。難しいバグは 1 件・各 10 回、著者は計測サイト TokenSave の運営者。

試すなら: .claude/agents/ の実装係に model: haiku、レビュー係だけ model: opus を置き、まず仕様がテストで書けているタスクで比べる → 許可は記事と同じ最小構成（Bash(npm test)・Bash(node:*)・読み取り専用 git。Flutter なら Bash(flutter test:*)）にして、claude -p --output-format json の total_cost_usd と usage で 1 回ごとの費用を記録する → 失敗が「報告にないケース」に偏るなら、そこだけ Opus に回す（記事の L6 がそれ）。163 回分のデータは CC BY 4.0 で tokensave.app/data/ai-coding-limit-line に公開。

FlutterFire 5.1.0（10/23）: cloud_firestore 7.1.0 に FieldValue.minimum()／maximum()（今の値と比べて小さい方・大きい方をサーバー側で書く）と Pipeline の findNearest に距離を返すフィールド名、firebase_ai 5.1.0 に TextPart の SpeechMetadata。全パッケージで Android SDK 35.0.2 と Gradle の代入記法修正、iOS は侵害された eMudhra 系ルート証明書を削除

— 10/16 の 5.0.0（minSdk 24）に上げた人の最初のマイナー。同時更新で壊れやすい「最小値・最大値の更新」が increment と同じ書き方で済む。

10/23 の BoM 5.1.0 で主要パッケージが同時更新。Firestore の FieldValue.minimum(値)／maximum(値) は set／update で「今の値と比べて小さい（大きい）方」をサーバー側で書く。読んで比べて書く往復が要らず、同時更新でも負けない（フィールドが無ければその値）。Pipeline の findNearest は距離を入れるフィールド名を指定でき、Android で無視・iOS で落ちていた分も直った。含意: 最小・最大の更新はトランザクションを書かずに済む。

試すなら: pubspec を firebase_core: ^5.1.0・cloud_firestore: ^7.1.0・firebase_auth: ^7.0.1・firebase_ai: ^5.1.0 にして flutter pub get → ハイスコアや最安値のように「今より良い時だけ更新」する欄は doc.update({'bestScore': FieldValue.maximum(score)})（トランザクション不要。flutterfire #18697）→ ベクトル検索で距離も要るなら Pipeline の findNearest に距離用フィールド名を渡す（#18838、Android／iOS／Web SDK と同じ指定）→ 5.0.0 の minSdk 24・Apple SDK 13 の条件はそのまま。Firebase release notes 10/23 にも Flutter SDK v5.1.0 が載った。

出典: pub.dev — cloud_firestore 7.1.0 changelog

DB の読みにくさだけで Claude Code の費用が 1.9 倍: 同じ EC データで命名・コメント・型・外部キーだけ変えた 2 つの DB に同じ集計クエリを 5 回ずつ頼むと、$0.21→$0.41、ターン 18.8→26.2、60→109 秒、実 DB を叩く Bash 5.0→11.8 回。読みにくい側は 5 回中 1 回、書かれていないタイムゾーンを推測して誤答（北野氏、10/23）

— AI に読ませる前提でスキーマのコメントと命名を整えるのは費用対策になる。Firestore なら「フィールドの意味・型・時刻の基準」を CLAUDE.md かスキーマ文書に書く、に置き換わる。

北野氏（10/23）。MySQL の EC データで、A は英単語の命名・カラムコメント・Enum、B は略語とローマ字・コメントなし・sts = 9・prc_a／prc_b。claude -p（Sonnet 5.5）に同じ命令を 5 回ずつ。平均費用 $0.21 対 $0.41、ターン 18.8 対 26.2、output 7,050 対 13,215、Bash 5.0 対 11.8 回。B の 1 回は odt が JST と書かれておらず UTC 変換して不正解。含意: 書かれていない前提は AI が推測で埋める。n=5・検定なし。

試すなら: 自分のスキーマで「AI が推測で埋めそうな前提」を 3 つ探す（時刻の基準、状態コードの意味、金額が税込か）→ MySQL ならカラムコメントと Enum、Firestore なら CLAUDE.md か docs/schema.md に「orderedAt は JST の Timestamp」「status は cancelled 等の文字列」と 1 行ずつ → 測るなら同じ依頼を claude -p --output-format json で 5 回流し、total_cost_usd と num_turns を前後で比べる。
