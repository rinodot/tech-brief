Claude Code の費用は「文脈の長さ×リクエスト数」。62 セッション・6,343 リクエストの実測で入力の 98.2% はキャッシュの読み直し、13 日続けたセッションの 1 往復は約 84 万トークン＝新規セッションの 31 倍。ツール呼び出しは 84.2% が 1 メッセージ 1 回、サブエージェント定義は 21,095 リクエストで 0 回→CLAUDE.md に常時指示を書いたら 27 セッションで 11 回（r.iguchi 氏 11/5）

— 週次上限を削るのは出力でなく毎往復の読み直し。CLAUDE.md の 2 行と /compact の残し方で、往復の数と 1 往復の重さを両方減らせる。

r.iguchi 氏（ムクイル技術ブログ、11/5）が 62 セッション・6,343 リクエストの会話ログ（~/.claude/projects/ の jsonl）を集計すると、入力トークンの 98.2% はキャッシュ読み込みだった。13 日使い続けたセッションの後半は 1 リクエストあたり約 84 万トークン（約 $0.42）、新規セッションは約 2.7 万（約 $0.013）で 31 倍。費用は「文脈長×リクエスト数」で決まる。

対策は 3 つ。ツール呼び出しは 84.2% が 1 メッセージ 1 回（平均 1.17）で、平均 2 にできればリクエストは約 41% 減る試算。サブエージェント定義は 97 セッション・21,095 リクエストで一度も使われず、CLAUDE.md に「常時使う」と書いたら次の 27 セッションで 11 回使われた。含意: 定義ファイルを置くだけでは呼ばれない。CLAUDE.md の常時指示と /compact の残し方で文脈を細く保つのが、上限対策の本丸。

試すなら: CLAUDE.md に「依存のないツール呼び出しは 1 メッセージにまとめる」「巨大ファイルは code-explorer サブエージェント経由で読む（常時有効な指示）」の 2 行 → .claude/agents/code-explorer.md に tools: Read, Grep, Glob・model: sonnet と「結論と file:行、最小限の引用だけ返す」 → 区切りごとに /compact 判定結果・変更対象の file:行・残作業だけ残す（記事の文言）→ 効き目は ~/.claude/projects/ の jsonl の message.usage を (message.id, requestId) で重複除去して数える。単価は記事の仮定（cache read $0.50／100 万）。

手書き Provider 261 件を @riverpod へ全面移行。改名だけの PR（86 宣言・2,193 箇所・276 ファイル）を先に 1 本出すと並行する子 PR のファイル衝突がゼロになり、統合 PR 744 ファイル・約 3 万行でもテスト 4,414 件が全部通った。落とし穴は autoDispose の既定・overrideWith・riverpod_lint の無言 exit 0（シンタク氏／日本トレカセンター 11/5）

— Riverpod 3 への移行で詰まるのは書き換えより PR の切り方と「通ったように見える」lint。個人アプリの規模でも段取りは同じ。

シンタク氏（日本トレカセンター、11/5）は手書き Provider 261 件を @riverpod へ移した。先に改名だけの PR（86 宣言・2,193 箇所・276 ファイル）を出すと以後の子 PR はファイルが重ならず、統合 PR 744 ファイル・約 3 万行でもテスト 4,414 件が全部通った。落とし穴は @riverpod の既定が autoDispose、overrideWith が build() を実行、riverpod_lint は読み込み失敗でも exit 0。件数は棚卸しスクリプトを唯一の基準にした。

試すなら: 保持したい Provider は @Riverpod(keepAlive: true)（riverpod.dev: 生成版は「購読が無くなると state を破棄」が既定）→ 手書きのまま変数名だけ生成名に揃える PR を先に 1 本 → 棚卸しスクリプト（手書き宣言・extends StateNotifier・legacy import が 1 件でもあれば失敗）に --check を付けて CI へ → dart analyze の「診断 0 件・exit 0」は riverpod_lint が動いた証拠にならないので、わざと違反を 1 つ書いて検知されるか確かめる。riverpod_generator 4.0.8／riverpod_annotation 4.0.6、Flutter 3.47.1。

エラー監視（Sentry）のアラートで Claude Code の Routine を API から起動し、Read・Glob・Grep だけで調べて Slack に 1 通報告させる構成。中継は署名を検証して決まった項目だけ渡し、起動 API は冪等でないので再試行は 429・5xx・通信失敗のときだけ（栗田基成氏／DeLT 11/5）

— Crashlytics の新規致命的問題を Cloud Functions の alerts トリガーで受ければ同じ型が組める。Routines の「起動の実例」にようやく 1 つ出た。

栗田基成氏（DeLT、11/5）の構成は、Sentry のアラート→Cloudflare Workers の中継→Routine の起動 API→Slack に 1 通。中継は Sentry-Hook-Signature を検証して不一致は 401、決まった項目だけを渡す。Routine の権限は Read・Glob・Grep の 3 つ、Slack は slack_send_message だけ。起動 API は冪等でないので再試行は 429・5xx・通信失敗だけ。ログは外部が書けるので注入前提の設計。効果・費用の数字はない。

試すなら: 中継から POST https://api.anthropic.com/v1/claude_code/routines/{id}/fire（Authorization: Bearer。docs/en/routines、10/19 既報）→ Routine のツールは Read・Glob・Grep と Slack の送信 1 本に絞り、シェル・git・編集は渡さない → Crashlytics なら firebase-functions/v2/alerts の onNewFatalIssuePublished（公式 docs/functions/alert-events）で受け、event.data.payload.issue の id・title・appVersion だけを渡す → 同じ issue id は一定時間起動しない。
