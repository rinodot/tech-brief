hanafusay氏（9/17）は paths のない rules 14ファイルと auto memory をやめ、AGENTS.md（短い原則と索引）＋Skills（依頼の種類で決まる手順）＋docs/（事実）に分けて、起動時のトークンが約41,500→約16,700。内訳は rules 約19,500・MEMORY.md 約4,600・Skills の説明一覧 約10,000で、消えたのは常時読み込みの rules と memory。含意: 毎回読ませる価値があるのは短い原則と索引だけで、手順は Skills に置けば呼ばれた時だけ読まれる。

本番の Firestore ルールが allow read, write: if true だった — Firebase MCP で本番を読んで直し、rules-unit-testing でテスト 28 件を足すまで実働 6時間40分

— 自分のアプリのルールを「最後に見たのはいつか」を思い出せないなら、同じ手順で今日確認できる。

ニイジマ氏（9/13、Next.js＋Firebase）。2人用カレンダーアプリの本番ルールを Firebase MCP で取得したら allow read, write: if true。手順は 本番を読む→前回反映した commit と照合→修正→デプロイ→再照合。@firebase/rules-unit-testing のテスト 28 件をエミュレータで追加。「getBlob() には CORS 設定が必要」という AI の説明は実測で不要だった。含意: 本番を MCP で「読む」工程を挟むと、AI の説明でなく実物を起点に直せる。

試すなら: claude mcp add firebase -- npx -y firebase-tools@latest mcp → 「firebase_get_security_rules で本番の Firestore ルールを取得して、リポジトリの firestore.rules と差分を出して」→ 直したら firebase emulators:exec "npm test" でルールのテストを回す（ツール名は Firebase 公式の MCP ページで確認済み）。

ローカルLLMに「判断だけ」させる — Ollama で num_predict=1 なら1回 33ms。接続先を localhost と書くと IPv6 の空振りで毎回 2 秒遅くなる

— hooks の判定器に 16GB の GPU を使う型。速さの落とし穴はモデルではなく接続先の書き方だった。

circle氏（9/18、Ollama）。「測っていないことを断定した文」を CLAUDE.md や memory に書いた直後に警告する hook の判定器。num_predict=1・temperature=0 で応答中央値は qwen3:14b 33.2ms、gemma4:12b 72.8ms。正答率は単体 53〜73%、二段構成で 96.7%（誤検出0・見逃し1）。localhost だと ::1 を先に引く分、67.8ms が 2,130.8ms に。含意: 判定は1トークンで足り、遅いのはモデルでなく経路。

試すなら: hook から叩く URL を http://127.0.0.1:11434/api/chat にし、"think": false と "options": {"num_predict": 1, "temperature": 0} を付ける → 同じ質問を選択肢の順を逆にして2回投げ、答えが変わらないか見る（変わるなら二段構成にする）。実装の3行は著者の有料本にあり、記事は測定結果のみ。

出典: Zenn — 判断だけさせるローカル LLM のすすめ
