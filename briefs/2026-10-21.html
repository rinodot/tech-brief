サブエージェントのキャッシュだけ 5 分枠だった: 約 7 分空けて呼び直すと料金 2.26 倍、.claude/settings.json の "subagentPromptCacheTtl": "1h" 1 行で払い直しが消え、定義に tools: [] と書くとキャッシュ対象が 26,310→1,643 トークン。公式 docs の裏取り: サブエージェント・ワークフロー・圧縮はサブスクでも既定 5 分、v2.1.242 以降で枠を選べる（ぬまーん氏、10/20）

— 補助役を数分おきに呼ぶ運用（監視→判断、レビュー役の往復）は、本体より先にサブエージェント側のキャッシュが切れて静かに割高になる。設定 1 行で直せる種類の無駄。

ぬまーん氏（10/20）。「PONG」と返すだけのサブエージェント課題を、呼ぶ間隔だけ変えて 16 回実行した（Claude Code 2.1.296）。本体のキャッシュは 1 時間枠（約 8,140 トークン）なのに、サブエージェントは 5 分枠（713 トークン）。5 秒後の再実行は 0.0128 USD、約 7 分空けると 0.0289 USD（2.26 倍）で、サブエージェントが 6,692 トークンを払い直していた。

.claude/settings.json に {"subagentPromptCacheTtl": "1h"} を書くと、6 分 51 秒後も 13 分 46 秒後も 0.0128 USD で払い直しなし。ただし 1 時間枠は書き込み単価が高く、同じ 26,310 トークンの初回は 0.1087→0.1457 USD（1.34 倍）。定義を tools: [] にするとキャッシュ対象は 26,310→1,643 トークン。公式 docs も「サブエージェント・ワークフロー・圧縮はサブスクでも 5 分」と明記。含意: 数分おきに呼ぶ補助役は 1h、連続で叩く用途は 5m のまま。n=1、費用は API 換算。

試すなら: claude -p "hello" --output-format json の usage.cache_creation（ephemeral_1h_input_tokens／ephemeral_5m_input_tokens）で今どちらの枠かを見る → 作業フォルダの .claude/settings.json に {"subagentPromptCacheTtl": "1h"}（v2.1.242 以降。環境変数 CLAUDE_CODE_SUBAGENT_PROMPT_CACHE_TTL=1h でも可、比較は FORCE_PROMPT_CACHING_5M=1）→ 特定のサブエージェントだけなら frontmatter の experimental: に cacheTtl: 1h（v2.1.248 以降。usage credits を消費中は 1h が無視される）→ 補助役の定義は tools: [] か必要な道具だけ列挙し、初回のキャッシュ書き込みを小さくする → 効果は /usage の Prompt cache (main) 行（v2.1.251 以降）とサブエージェントの total_cost_usd で比べる。5 分以内に連続で呼ぶ用途は 1h にしない（書き込み 1.34 倍だけ損）。

Flutter の PlatformView 新方式 HCPP（Hybrid Composition++、3.44 から実験的）を実機で計測: 従来 HC はメインスレッド 4ms の負荷でジャンク率 84.8%・74.5 FPS に崩れ、HCPP は 2.7%・121.0 FPS を維持。条件は Android 14 以上＋Impeller の Vulkan、AndroidManifest.xml の meta-data 1 つで有効化、満たさない端末は自動で従来方式（ogikun 氏、10/20）

— 広告バナー・地図・WebView を載せた Flutter 画面のカクつきは PlatformView 合成の問題であることが多い。公式が「実験的」のうちに自分の端末で測れる。

ogikun 氏（10/20）。Galaxy Z Fold7（Android 16）・Flutter 3.47.7 の profile で 15 秒スクロール×3 回の中央値。負荷なしの FPS／ジャンク率は TLHC 120.4／0.7%、HC 94.8／63.3%、HCPP 121.2／0.4%。メインスレッドに 4ms 足すと HC は 74.5／84.8% に崩れ、HCPP は 121.0／2.7%。8ms では HCPP も 69.7／62.9% で TLHC 並み。含意: HCPP は TLHC と同等、HC だけ別格に崩れる。n=1、実験的機能。

試すなら: Flutter 3.44 以上で flutter run --enable-hcpp（flutter test も可、flutter build には付けられない）→ 本番は AndroidManifest.xml の <application> 内に <meta-data android:name="io.flutter.embedding.android.EnableHcpp" android:value="true" />（公式 docs）→ 記事の確認法: debug で adb logcat | grep "platform view rendering strategy" に Using HCPP… か legacy… が出る → 自作 PlatformView は HybridAndroidViewController.checkIfSupported()（api.flutter.dev に記載）で判定し、false なら従来 API へ → 既知の制限: 透明な PlatformView の 4 層重ね、BackdropFilter・ImageFilter・StretchingOverscrollIndicator が効かない。Android 13 以下の端末では従来方式のままなので、両方で測る。

出典: Zenn — Flutter で地図や WebView を置くと重くなる問題、新方式 HCPP で解決するのか検証した
